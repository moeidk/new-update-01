# راهنمای جامع راه‌اندازی و مدیریت سیستم استقرار دو مرحله‌ای (Staging & Production)

این راهنما فرآیند کامل راه‌اندازی، اتصال مخزن GitHub به Cloudflare Pages، پیکربندی متغیرهای محرمانه (Secrets)، نحوه کار با سیستم اعلان در پنل React و استراتژی مصون‌سازی داده‌های کاربران را گام‌به‌گام توضیح می‌دهد.

---

## ۱. نقشه راه و چرخه حیات توسعه و انتشار (Workflow)

```
[۱. توسعه تغییرات توسط هوش مصنوعی/برنامه‌نویس روی برنچ جدید (مثلاً feature/update)]
                                      │
                                      ▼
                      [۲. ارسال Push به برنچ جدید در GitHub]
                                      │
                                      ▼
             [۳. اجرای تست‌ها و لینت در GitHub Actions]
                                      │
                                      ▼
             [۴. استقرار خودکار روی محیط Staging (Cloudflare Pages Preview)]
                                      │
                                      ▼
       [۵. بررسی و تست نسخه پیش‌نمایش در آدرس اختصاصی توسط شما (مدیر)]
                                      │
                                      ▼
  [۶. مشاهده اعلان در پنل React: «نسخه جدید آماده انتشار است»]
                                      │
                                      ▼
     [۷. کلیک روی «انتشار روی سایت اصلی» یا تایید دستی در GitHub Environments]
                                      │
                                      ▼
           [۸. استقرار امن نسخه نهایی روی دامنه اصلی (Production)]
                                      │
                                      ▼
    [۹. اجرای مایگریشن خودکار (Idempotent) در مرورگر و حفظ ۱۰۰٪ داده‌های کاربران]
```

---

## ۲. گام اول: پیکربندی Cloudflare Workers و Wrangler

پروژه به صورت کامل با **Cloudflare Workers** و اکشن رسمی **`cloudflare/wrangler-action@v3`** یکپارچه شده است:
۱. فایل پیکربندی `wrangler.toml` در ریشه پروژه قرار دارد که خروجی فرانت‌اند (`dist`) را به عنوان Single Page Application مدیریت می‌کند.
۲. دو محیط مجزا برای استقرار تعریف شده است:
   - **Staging / Preview**: با دستور `wrangler deploy --env staging`
   - **Production**: با دستور `wrangler deploy --env production`
۳. همچنین نسخه موتور Node.js روی **Node 22 LTS** تنظیم شده تا هشدارهای منسوخ شدن برطرف شوند.

---

## ۳. گام دوم: ساخت محیط Production و Reviewer در GitHub

برای اینکه هیچ کدی بدون تایید صریح شما مستقیماً روی سایت اصلی منتشر نشود:

۱. در مخزن گیت‌هاب خود به تب **Settings > Environments** بروید.
۲. روی دکمه **New environment** کلیک کنید و نام آن را `production` بگذارید.
۳. تیک گزینه **Required reviewers** را فعال کرده و نام کاربری خود در گیت‌هاب را به عنوان Reviewer مجاز انتخاب کنید.
۴. در این حالت، هر زمان که جاب `deploy_production` اجرا شود، گیت‌هاب منتظر تایید صریح شما می‌ماند و بدون آن هیچ دامنه‌ای تغییر نمی‌کند.

---

## ۴. گام سوم: تنظیم متغیرهای محرمانه (GitHub Secrets)

در مخزن گیت‌هاب به مسیر **Settings > Secrets and variables > Actions** بروید و متغیرهای زیر را ثبت کنید:

| نام متغیر (Secret) | توضیح |
| :--- | :--- |
| `CLOUDFLARE_API_TOKEN` | توکن ایجاد شده در کلودفلر با دسترسی `Cloudflare Workers: Edit` یا `All accounts - Edit` |
| `CLOUDFLARE_ACCOUNT_ID` | شناسه حساب کاربری شما در کلودفلر (Account ID) |

در سرور بک‌اند و فایل `.env` نیز متغیرهای زیر را قرار دهید:
```env
# نام کاربری مدیر در سایت
VITE_ADMIN_USERNAME="admin"

# کلید مخفی احراز هویت ادمین برای تایید تریگر استقرار
ADMIN_SECRET_KEY="your_super_secret_admin_key"

# توکن گیت‌هاب با دسترسی repo و workflow (برای تریگر اتوماتیک)
GITHUB_TOKEN="ghp_xxxxxxxxxxxxxxxxxxxx"
GITHUB_REPO_OWNER="your_username"
GITHUB_REPO_NAME="keeppass-vault"
```

> **نکته بسیار مهم امنیتی:** توکن `GITHUB_TOKEN` تنها در سمت بک‌اند یا در متغیرهای سرور نگهداری می‌شود و **هرگز** در کد فرانت‌اند یا مرورگر کاربر قرار نمی‌گیرد.

---

## ۵. گام چهارم: نحوه کارکرد نوتیفیکیشن در پنل React

۱. در زمان بیلد، اسکریپت `scripts/generate-version.js` فایل `public/version.json` را با اطلاعات زیر تولید می‌کند:
   - شماره نسخه (`version`)
   - هش کامیت گیت (`gitCommit`)
   - زمان دقیق بیلد (`buildTime`)
   - لاگ تغییرات (`changelog`)
۲. سرویس `src/services/updateDetector.ts` هر ۹۰ ثانیه و هنگام بازگشت به پنجره مرورگر، این فایل را با هدرهای ضد-کش استعلام می‌کند.
۳. اگر شما با نام کاربری مدیر لاگین کرده باشید:
   - یک بنر شکیل با متن **«نسخه جدید آماده انتشار است»** ظاهر می‌شود.
   - با کلیک روی **«انتشار روی سایت اصلی»**، درخواست شما با کلید ادمین به اندپوینت `/api/trigger-deploy` ارسال شده و اکشن دیپلوی اجرا می‌شود.
   - با کلیک روی **«بعداً»**، اعلان موقتاً به تعویق می‌افتد.
   - در تب **تنظیمات > استقرار و آپدیت (DevOps)** نیز همواره امکان بررسی دستی و دانلود بکاپ وجود دارد.

---

## ۶. گام پنجم: تضمین حفظ ۱۰۰٪ داده‌های کاربران (Data Preservation & Migration)

چگونه مطمئن شویم هیچ رمزی در جریان آپدیت پاک نمی‌شود؟

### ۱. معماری Idempotent
تابع `DataMigrationService.runMigrations()` در لحظه لود اولیه برنامه در `App.tsx` اجرا می‌شود. این تابع بررسی می‌کند که آیا فرمت ذخیره‌سازی قبلاً ارتقا یافته است یا خیر؛ اگر بله، هیچ تغییری ایجاد نمی‌شود.

### ۲. پایداری داده‌های رمزنگاری شده (Web Crypto API)
- اطلاعات گاوصندوق به صورت رشته‌های رمزنگاری شده `AES-GCM` همراه با سالت و IV در کلیدهای مجزا به تفکیک نام کاربری ذخیره شده‌اند.
- در فرآیند آپدیت و رفرش، هیچ دستوری مبنی بر `localStorage.clear()` وجود ندارد و تمام شناسه‌ها پایدار می‌مانند.

### ۳. اسنپ‌شات خودکار محلی
قبل از اعمال هرگونه مهاجرت یا تغییر در کلیدها، سامانه یک نسخه پشتیبان کامل از کلیدهای مرتبط در `localStorage` با پیشوند `__keeppass_migration_backup_` ایجاد می‌کند تا در صورت نیاز به رول‌بک، داده‌ها دست‌نخورده باقی بمانند.

### ۴. دانلود نسخه پشتیبان دستی
در تب **استقرار و آپدیت (DevOps)**، دکمه‌ای تعبیه شده که با زدن آن، یک فایل JSON حاوی تمامی کلیدها و رکوردها به عنوان نسخه اطمینان بر روی هارد دیسک شما ذخیره می‌شود.

---

## ۷. گام ششم: اسکریپت پشتیبان‌گیری سرور قبل از دیپلوی

قبل از اجرای هر دیپلوی، اسکریپت زیر در محیط سرور/گیت‌هاب اجرا می‌شود:
```bash
./scripts/backup-db.sh
```
این اسکریپت:
- پوشه آرشیو با تاریخ و ساعت ایجاد می‌کند.
- از دیتابیس (PostgreSQL یا SQLite) بکاپ می‌گیرد.
- فایل متادیتای بیلد قبلی را ذخیره می‌کند.
- فایل فشرده `.tar.gz` تولید کرده و هش `sha256` را محاسبه می‌کند.
- نسخه‌های قدیمی‌تر از ۱۰ نسخه اخیر را به صورت خودکار پاکسازی می‌نماید.

---

## ۸. روال روزمره برای هوش مصنوعی و تیم توسعه

1. هوش مصنوعی یا توسعه‌دهنده تغییرات جدید را در یک برنچ تست (مانند `staging-v1.1`) کامیت و پوش می‌کند:
   ```bash
   git checkout -b staging-v1.1
   git add .
   git commit -m "feat: New security features and layout improvements"
   git push origin staging-v1.1
   ```
2. اکشن گیت‌هاب به صورت خودکار پروژه را تست کرده و محیط Preview در کلودفلر می‌سازد.
3. شما لینک Preview را در تلگرام یا گیت‌هاب دریافت کرده و عملکرد را چک می‌کنید.
4. در صورت تایید، وارد پنل اصلی شده و دکمه **«انتشار روی سایت اصلی»** را می‌زنید (یا PR را به `main` مرج می‌کنید).
5. سایت اصلی بدون ثانیه‌ای قطعی به‌روزرسانی شده و داده‌های کاربران ۱۰۰٪ مصون می‌مانند.
